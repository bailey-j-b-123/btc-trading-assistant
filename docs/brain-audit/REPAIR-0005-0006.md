## 2. What changed

1. `src/trading_assistant/web/chart_evidence.py`
   - retest branch: `reference_type`, `reference_id` (from `event.breakout.reference`) and the
     retest candle's own `close`; failed-breakout branch: `reference_id` and the re-entry candle's
     own `close`. Both closes make `close_at_event` / `position_at_event` real for those kinds
     (they were unconditionally `null`).
2. `src/trading_assistant/web/zone_evidence.py`
   - the exact matcher is **unchanged** (zone reference, Decimal-equal bounds, `known_at <= as_of`);
   - a second, clearly separated pass reports **contained references** — a smaller recorded band
     inside the band's (or a member zone's) bounds — from the same filtered candidates, so kind,
     type, bound and causality rules are identical; a record already reported as an exact link is
     never repeated; each record carries `match` (`exact`/`contained`) and `linked_via_bounds`;
   - `EMPTY_LINKAGE` and `NOT_EVALUATED_LINKAGE` both gain the `contained_*` fields, with
     `contained_count` `0` when checked and `null` when not evaluated, so "unchecked" can never be
     read as "nothing there";
   - `CONTAINED_NOTE` states both facts when a band has contained references but no exact links.
3. Front end — `explain.js` (`linkedEventSentence`, `linkedRows`), `function_panel.js`
   (`linkedEventText`) and `dashboard.js` (new exported `zoneEventNote`): exact links keep their
   existing wording; contained references get their own wording that says it is an observation of
   earlier bounds, not identity; an unchecked view still reads "not checked on this view".

No detector threshold, stage, plan, journal or ledger record is touched.

## 3. Why the evolved bands are reported as contained, not as identical

That is the honest result, not a workaround: at `as_of=2026-10-14T00:00Z` the displayed band is
`85958.6 – 87052.5` while every event recorded against that level holds `85958.6 – 86543.0` or
`86543.0 – 86543.0`. The zone was *re-derived* wider as later swings confirmed; the events keep
the band they were actually detected with. Reporting those as an exact link would be false; the
containment fact is reported instead, with both sets of bounds and the event's own instant
visible, and the strict identity rule still fires where it truly holds (the positive control at
`2026-08-26T08:00Z`, and the pinned synthetic series at the 375/400/500 decision boundaries,
where 8, 6 and 2 previously invisible retests now link exactly).

## 6. Verification limitations (stated plainly)

- **Browser checks could not be executed in this sandbox.** `scripts/browser-audit/
  support-resistance-check.mjs` needs a Chromium with system libraries (libnspr4/libnss3) that are
  absent; there is no root to install them, and the browser-download hosts are outside this
  environment's allowlist. This is a limitation of the environment, not a result: the check was
  **not run** here, and no browser pass is claimed. What was verified instead: the wording is
  covered by the Node suites above, and the new sentence lives in the explanation's `state`
  section, which renders inside the collapsed `<details>` ("Why, timing and influence") — the
  element the browser check reads via `innerText` excludes collapsed content, and the visible
  first section is unchanged, so the check's claim-free assertion is structurally unaffected.
  **A rechecker with the browser toolchain must run it.**
- All candles used by the tests are the repository's own **synthetic** demonstration data,
  explicitly labelled; no genuine stored market history is available in this environment.
- The digest fixture regeneration is documented above and in the test docstring; it is a
  presentation-payload fixture, not a decision fixture.
