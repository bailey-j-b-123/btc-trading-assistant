## E. The existing S/R timeframe-switch check, on its documented configuration

Three consecutive runs against the 1H-engine demo server (the configuration its usage documents):
```
$ node scripts/browser-audit/support-resistance-check.mjs http://127.0.0.1:8125/ <out> --timeframe 1h --switch 4h

support-resistance check passed at 4 viewports; report: /home/user/btc-trading-assistant/.cache/verify/browser/sr-repair-run3/support-resistance-report.json
```

Configuration trap, recorded so it is not mistaken for an application defect later: that check's
first phase reads the painted bands as soon as the timeframe button reports pressed, which on a
server whose ENGINE timeframe differs from the `--timeframe` it is given (e.g. `--timeframe 1h`
against the 4H-engine server on port 8126) happens before the newly requested view has applied.
It then compares the previous view's bands with the requested timeframe's API bands and fails 29
assertions. An independent probe of the same server and view shows the application is correct:
once the 1H view has settled it paints the 1H band alone (`IN 1H · 37×` at
87,062.80 – 88,142.20, equal to `/api/market/structure?timeframe=1h`), and the engine-timeframe
card lists the engine's own 4H bands, exactly as designed. Run that check against a server whose
engine timeframe matches its `--timeframe`, as its own usage block does.
